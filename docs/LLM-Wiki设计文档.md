## 1. 背景与设计问题

### 1.1 为什么"让 AI 建个双链 wiki"不成立

对 AI 说"给我按双链建 wiki"，得到的是**一批带 `[[]]` 语法的文档**——双链只是输出格式。LLM 维护知识库有三个先天失效模式：

| 失效模式 | 表现 |
|---------|------|
| **无跨会话记忆** | 每次会话从零开始，上次命名 `con-配置中心`，这次写成 `con-ConfigCenter`，重复页与死链从第一天就开始累积 |
| **输出不稳定** | 同一任务两次执行的产物不一致；抑制条件靠"记住规则"，但记忆不可靠 |
| **会编造** | 转述数字、版本号、日期时无中生有，且与真实论断混排，人眼难辨 |

因此本设计的核心命题是：**把对 AI 的"嘱咐"换成可执行的"机制"**——体系必须不依赖 AI 的自觉也能自洽运转。

### 1.2 设计目标

1. **跨会话自洽**：第 N 次会话仍然可用，知识库不随时间腐化
2. **可验证**：承重事实可机器核对，AI 写错能被抓出来
3. **可协作**：入库内容与个人环境（盘符、路径、工具）解耦

## 2. 三条元原则（先于一切要素）

| 原则 | 含义 | 反例 |
|------|------|------|
| **P1 症状驱动** | 每条规则必须对应一个已经实际发生的失效模式 | 为想象中的多 agent 并发写锁机制 |
| **P2 机制优先于嘱咐** | 能机器验证的不靠自觉，能结构化的不写进散文 | "AI 要注意不要写错数字"❌ → locate-before-write ✅ |
| **P3 单一职责** | 每个字段/文件/规则有唯一职责；冗余即漂移源 | `type: source` 字段与文件名前缀三重冗余 |

## 3. 最小五要素（体系骨架）

**判断标准：去掉任何一个，体系在跨会话场景下无法自洽运转。** 五条合计不到半页纸，即构成一个最小可用的 LLM-Wiki。

| # | 要素 | 没有它的失效模式 | 落点 |
|---|------|----------------|------|
| 1 | 寻址稳定（一页一物） | 重复页 + 死链，知识库从第一天腐蚀 | 文件名 = 全局唯一 ID |
| 2 | 确定性入口（检索面） | AI 检索靠全目录扫描和猜文件名，行为不可复现 | 每次操作从可复现的检索面开始 |
| 3 | 读写边界 | AI "顺手整理"原始文档，事实层被污染且不可逆 | docs/ 只读，wiki/ 唯一可写 |
| 4 | 可溯源 | AI 推断与事实混淆，无法回答"依据是什么" | 每页必须声明证据坐标 |
| 5 | 连带更新 | 单点写入，关联页引用旧结论，库内矛盾累积 | 写任何页面 = 同步更新受影响页与检索面 |

### 3.1 寻址稳定（一页一物）

- **是什么**：文件名格式固定（`con-<概念名>` / `src-<标识>`），所有链接与目标文件名完全一致；建页前先查检索面，近似概念**更新而非新建**。
- **为什么**：双链的本质是"文件名即全局 ID"。ID 不稳定，一切上层结构（链接、索引、图谱）全部失效。
- **关键洞察**：要素要求的是"规则**存在且确定**"，而不是规则的具体内容——标识用什么语言、要不要前缀都是实例化，一旦定死永不更改即可。
- **失效症状（若缺失）**：同一概念两个页面互相不知道对方存在；第三方引用随时间全部变成死链。

### 3.2 确定性入口（检索面）

- **是什么**：任何 Wiki 操作（读或写），第一步经过同一个可复现的检索面——文件枚举、本地 index、MCP 检索三选一，按规模阶梯选择（见 §9.2）。
- **需求与实现分离**：要素要求的是"检索行为可复现"，不要求"index 文件存在"。要素 1（寻址稳定）使文件名本身携带类型与主题信息，小库阶段"枚举文件名"即满足本要素；index 是规模化的实现（投影缓存），不是体系必需品。
- **为什么**：LLM 每次会话失忆，必须有一个每次都从同一处开始的 bootstrap 点。检索行为不可复现，"AI 找不到已存在页面 → 新建重复页"的事故率显著上升。
- **失效症状**：AI 回答"库里没有相关知识"但其实有；同一问题两次会话给出不同的页面集合。

### 3.3 读写边界

- **是什么**：`docs/`（原始资料、工程交付文档）只读；`wiki/` 是唯一可写区；冲突时以原文为准。
- **为什么**：事实层是整个体系的信任根基。AI 修改原文（哪怕出于好意的"整理"）会不可逆地破坏溯源链——验证脚本核对的是原文，原文被动过，"验证过的永远验证过"就不成立。
- **失效症状**：交付文档被 AI 润色后与 git/SVN 历史冲突；来源页摘要与"原文"逐字不一致但说不清谁对。

### 3.4 可溯源

- **是什么**：每个 wiki 页面必须声明证据坐标；无来源的论断不得写入（AI 的推断可以写，但必须标注"推断"并给出依据）。
- **为什么**：这是 LLM-Wiki 区别于"AI 写的笔记"的底线——没有溯源，AI 的推断和事实混在一起，知识库整体不可信。
- **失效症状**：页面里"42% 的用户…"到底是源文档说的还是 AI 编的，无人能回答。
- **注**：最小形态只需要一个强制的"来源"字段；坐标化（raw 字段）是扩展 1 的内容。

### 3.5 连带更新

- **是什么**：新建或更新页面时，检索 wiki 中引用了本页主题的既有页面，同步更新其中过时表述，并更新检索面（index 若启用）。
- **为什么**：知识是网状的，单点写入必然造成"综述页引用旧结论"的库内矛盾。此要素是五条中执行成本最高的，也是知识库"复利"的来源——每次录入让整张网变新，而不是只让一个点变新。
- **失效症状**：概念页已更新为 V1.3 语义，关联它的其他页面还在描述 V1.2 机制，且无人知晓。

## 4. 扩展能力：调整点与理由

**判断标准：去掉它体系照样跑，只是会踩特定的坑或规模变大后变糟。** 每项扩展按统一结构记录：触发症状 → 调整点（改哪里、为什么）→ 代价。

### 4.1 扩展 1：溯源坐标化（raw 字段）

**触发症状**：多人协作时个人盘符路径（`y:\`）在他人机器失效；跨仓库源文档引用悬空。

| 调整点 | 位置 | 为什么 |
|--------|------|--------|
| src 页 frontmatter 增加 `raw` 字段 | 模板 | 路径必须结构化才能被 lint/脚本解析；写在散文里的路径格式不可控 |
| 来源粒度一对一：一个 src 页 = 一个逻辑来源（共享版本号的文件群可用 `raw` 数组）；多源关系由 con 页来源区列表表达 | 模板/规则 | `version` 锚点、漂移检测、no-material 台账都以"单一证据坐标"为前提；karpathy 的多文件 Raw 字段与版本锚点不兼容，故多源性上移到 con↔src 关系层 |
| 跨仓库铁律：外部材料必须拷副本入 `docs/` | 规则 3 + 协议 | 外部仓库不受本仓库版本控制，"验证过的永远验证过"不成立；副本入库使证据随库版本化。同仓库文档**免拷贝**（避免双份漂移） |
| frontmatter 字段准入标准 | 约定 | 字段越多漂移面越大（P3）：`type` 与前缀冗余、`name` 与文件名冗余，均删除 |

**代价**：录入多写一个字段；跨仓库材料多一次拷贝动作。
**收益**：`raw` 人人可解析，零配置零路径冲突。

### 4.2 扩展 2：机器可验证的溯源（version 锚点 + 字面量保真）

**触发症状**：AI 转述数字/版本号出错无从发现；源文档升级后 wiki 页静默过时。

| 调整点 | 位置 | 为什么 |
|--------|------|--------|
| frontmatter 增加 `version`（语义锚点） | 模板 | "本页基于源文档第几版"是录入时刻的快照，不存在于任何其他地方；正文版本号不可替代（一页正文可出现多个版本号，机器无法判断哪个是锚点）。**不用 commit hash**：文档与 wiki 常同次提交，hash 无法区分版本语义，版本号才在内容坐标系里 |
| 写入端 locate-before-write | Ingest 协议 | 验证端只能"抓漏"，写入端规则把错挡在源头：每个数字/版本/日期写入前先在源文定位，找不到就不写精确值；源文写 42K 就写 42K |
| lint 增加两项：字面量保真 + 版本漂移 | Lint 协议 | 保真核对"写对没有"；漂移比对"源是否已升级"。两者失配的处置完全不同（改页面 vs 重新编译），有锚点才能区分 |

**依赖**：扩展 1（先有 raw 坐标，才有验证目标）。
**代价**：录入心智负担增加；无版本号的文档验证降级（接受，不硬造锚点）。

### 4.3 扩展 3：Triage 分诊（Ingest 的强制出口）

**触发症状**：薄来源被硬凑成页面，库内噪音累积；同一来源被反复录入。

| 调整点 | 位置 | 为什么 |
|--------|------|--------|
| Ingest 在编译前插入分诊步骤，**显式声明** disposition（New / Update / Disputed / No material） | Ingest 协议 | 抑制靠记忆不可靠（P2）；把"该不该录入"变成每次必经的出口判断 |
| No material 成为显式出口（停止，不产出页面） | Ingest 协议 | "不硬凑"从嘱咐变成流程分支 |

**依赖**：No material 的台账由扩展 5 承载（否则同一薄来源日后被反复 triage）。

### 4.4 扩展 4：Status 块（过时/争议的标准处置）

**触发症状**：源文档语义级变更后，con 页要么静默改写（丢兼容性历史），要么散装标注（🔴/⚠️ 格式失控、lint 无法检查）。

| 调整点 | 位置 | 为什么 |
|--------|------|--------|
| 固定格式块：`**Status: Outdated/Disputed** (日期) + 说明 + 来源`，紧贴受影响论断下方 | 模板 | 格式固定才可机械检查；紧贴论断保证读者读到警示（放页面顶部会被漏看） |
| **旧论断不删**（never silently rewrite history） | 规则 | 旧事实 ≠ 无用事实：旧版本存量环境的兼容性信息靠它保留（例：V1.2.x 部署的契约落点仍是 scripts/） |
| lint 增加 malformed Status 块检查 | Lint 协议 | 缺日期/缺说明的标注等于没标 |
| 与版本漂移闭环：漂移报警 → 复核 → 过时论断加块、有效论断改写并刷新锚点 | 跨协议 | 检测到过时之后必须有标准处置出口，否则退回静默改写或散装标注 |

**依赖**：与扩展 2 闭环（漂移检测提供触发信号）。

### 4.5 扩展 5：操作日志（log.md）

**触发症状**：一来源牵动多页容易漏；无法审计"何时、基于何版本录入"；薄来源反复被 triage。

| 调整点 | 位置 | 为什么 |
|--------|------|--------|
| 目录结构增加 `log.md`（只追加，永不修改） | 结构 | 日志的价值在于不可篡改，改一条整条失信 |
| Ingest/Lint 协议末尾追加条目 | 协议 | 动作与事实分离：页面管知识（是什么），日志管动作（做过什么），各单一职责（P3） |
| src 页 `date` 语义简化为"源文档日期" | 模板 | 录入时间由日志条目承载，避免双处记录漂移 |

**代价**：每次写操作多一步；Query 不记录（防日志膨胀成流水账）。

**访问纪律**：log 只允许三种访问方式——追加（写所属小节末尾）、读尾部（最近 N 条）、grep 定点检索；**禁止全文读入上下文**。增长量化与并发结构见 §9.3 / §9.6。

### 4.6 扩展 6：Obsidian 双链生态

**定位**：必选扩展。本项目运行环境已统一部署 Obsidian 与 obsidian-mcp-pro，反向链接、图谱、语义检索、别名命中是知识库的基础设施而非可选项。

| 调整点 | 位置 | 为什么 |
|--------|------|--------|
| vault 根固定为 project-root | 环境 | 工程文档进 vault，wiki 页可双链回指交付物，获得"知识↔交付物"图谱（不再提供 wiki/ 作为备选根） |
| 链接语法定死 `[[页面名]]`，文件名全 vault 唯一升级为硬约束 | 规则 1 | Obsidian 按文件名解析双链、不认路径；同名即歧义。前缀命名天然防撞 |
| frontmatter 增加 `aliases` | 模板 | 让页面可被"其他叫法"命中；从源头防"换个叫法就建重复页"。别名从源文档实际用词来，不发明 |
| Query/Lint 换引擎（obsidian-mcp-pro：search_notes / get_backlinks / find_broken_links） | 协议 | 把"AI 用 grep 模拟"的检查换成原生索引 |
| index.md 降级为本地投影缓存（不提交，见 §9.2） | 规则 2 | 人靠 Obsidian 浏览 vault、AI 检索走 MCP，提交版 index 的消费者在本环境中为空集；不提交则头号冲突热点消失 |

**红利**：`[[页面名]]` 不依赖路径 → 目录重组零链接成本。
**代价**：脱离 Obsidian 的环境（GitLab 网页等）双链为死文本。

### 4.7 扩展 7：决策页类型（dec-）

**触发症状**：待裁定、技术债、注意事项在工作流中真实存在（MSDD 评审流程持续产生），但没有承载页——con 回答"是什么"（无时间性），src 回答"来源说了什么"，"当时为什么这么定 / 现在欠什么债 / 什么悬而未决"这类**带生命周期的知识**没有去处。

| 调整点 | 位置 | 为什么 |
|--------|------|--------|
| 新增 dec- 类型与模板（背景 / 决定 / 依据 / 关联） | 模板/命名 | ADR 是工程界成熟实践；决策是原子记录（非综述）、有状态、有日期——三个特征均为既有类型缺失 |
| 生命周期复用 Status 块：Resolved（已解决）/ Superseded（被 [[dec-xxx]] 取代） | 扩展 4 | 不发明新机制——关闭与 Outdated/Disputed 同一套格式、同一个 lint 检查 |
| raw 可选；无文档依据时在「依据」区写决策人与场合 | 规则 4 放宽 | 决策的证据常是会议而非文档，强制 raw 会逼人造假锚点——显式放宽优于含糊带过 |
| 独立操作入口（不经 Ingest） | 协议 | 决策诞生于对话，不来自文档流水线 |

### 4.8 扩展 8：主题综合页类型（syn-，"录像模式"）

**来源**：知识库管理演示的"录像示例"——需求/设计/调试三份孤立文档，一个主题页串联三块知识。

**类型决策：枢纽页定为 syn- 而非 con- 变体**。判据：页面离开多源聚合是否成立——con-能力契约 单独成立（它就是概念本身），主题枢纽离开三份文档的聚合不成立（跨源综合正是 syn 的定义）。同时避免 con 模板分裂成两个形态（标准概念型 / 三维度枢纽型），保持模板确定性。

**结构同构**：完整版 syn 模板与枢纽结构逐节对应——核心论点↔定义、详细论述↔需求/设计/调试要点（按知识维度切的子主题）、开放问题↔dec-、关联来源↔来源区。枢纽是 syn 的一个用例。

**严重缺点与对策**（懒建判据的由来）：

| 缺点 | 严重度 | 对策 |
|------|--------|------|
| con 层粒度无客观锚（主题切分主观 → 重复录入、漏更新） | 高 | 懒建：主题边界在反复查询中显形后再切分 |
| 三流汇一页（需求/设计/调试三条更新流汇入同一文件 → 冲突热点，"一页一物"的文件级隔离在此失效） | 高 | 小节化写入纪律：每次更新只动所属小节，不同文档流的更新落不同区域，git 行级合并自动通过（同 log 分小节原理） |
| 页面混合版本状态（三节依赖三文档三版本，页面级无锚点，漂移检测是 src 页粒度） | 中 | 接受；节末"依据 [[src-xxx]]"保持可追溯，混合窗口靠短周期 ingest 缩短 |
| 单点信任（AI 提炼错误随枢纽页持续传播，字面量保真查不出"理解错了"） | 中 | 人工复核 + 枢纽晚建缩短错误传播窗口 |
| 成本前置（预拼装的赌注：主题判定失误 = 沉没成本） | 低 | 懒建判据直接消除 |

**懒建判据与演化链**：默认只建 src 页；同一主题的知识拼装在查询中**重复发生**才建 syn（拼装成本的反复发生是值得预拼装的证据）：

```
src（默认，机械）→ con（概念沉淀）→ syn（主题综合，懒建）→ syn-<子主题>（膨胀拆分）
```

膨胀拆分**按子主题拆、禁止按文档类型拆回三页**——后者将复活演示第 1 页左边的"三块孤立"，枢纽的全部投入白费。拆分粒度对齐查询粒度（用户按子主题提问，不按文档类型提问）。

## 5. 扩展间依赖关系

```
扩展1 坐标化 ──→ 扩展2 可验证溯源 ──→ 扩展4 Status 块
                    （验证目标）          （漂移的处置出口）
扩展5 操作日志 ──→ 扩展3 Triage 的 No material 台账
                    （date 语义简化也依赖日志承载录入时间）
```

- **2 依赖 1**：无坐标无验证目标
- **4 与 2 闭环**：检测（漂移）与处置（Status 块）必须成对出现，只有检测没有处置等于报警器响了没人接
- **3 依赖 5**：No material 不留台账，薄来源会被反复 triage
- 引入顺序建议：1 → 2 → 5 → 3 → 4（先有证据坐标，才能验证；先有日志，台账和审计才成立）
- **增量更新（§9.4）依赖扩展 2 与扩展 6**：变更检测靠版本锚点，影响面靠反链——前面扩展的投入在增量更新处变现，依赖链闭环

## 7. 负面清单（明确不做，及理由）

| 不做 | 理由 |
|------|------|
| 向量/图检索 | 库规模（数万 token 级）grep + read 更可靠；召回劣化实测发生再加 |
| 置信度/质量分数 | 无校准依据的假精度；证据强度写在正文里 |
| 预置 ent/cmp/syn 页面类型 | 类型越多维护成本越高；出现对应需求再升级到完整版 |
| 行号级引用锚点 | 全文 grep 已覆盖观察到的失配模式；锚点摩擦会让执行者跳过规则 |
| 多 agent 并发锁 | 当前单会话串行场景，无该失效模式 |
| 按访问频次衰减权重 | 常被问 ≠ 是真的 |
| 自动定时 lint/hook | 属于宿主环境（agent harness）职责，不入工具无关的 skill |

## 8. 演进路线（lite → 完整版）

| 触发条件（症状） | 动作 |
|----------------|------|
| 命名出现"这次A下次B" | 标识语言写成显式强制约定 |
| 页面变多 / 团队偏好目录组织 | 子目录分区（按类型、按主题或任意约定方式；双链不依赖路径，重组零成本） |
| 需要对比类页面 | 增加 cmp- 类型（ent-/syn- 已转正：前者因库中实例，后者因三件套工作流的按需特化） |
| 矛盾/过时高发 | 完整版三档 Lint 权限与检查项清单（升级细则见 §8.1） |
| 与 MSDD 工程流融合 | 迁移到 `msdd/wiki/llm-wiki-skill.md` |

> 演进原则不变：每条新规则必须对应一个已经实际发生的症状（P1）。

### 8.1 升级细则：Lint 两档 → 三档

**性质变化**：lite 的 lint 是**审计工具**——检查项全部机械（字面量保真 / 版本漂移 / Status 块格式 / 断链孤儿），权限二元（要么确定地修，要么只报告）。完整版三档 lint 是**治理流程**——检查项含语义判断（矛盾 / 缺失 / 空白），权限三级（自动修 / 需用户确认 / 仅报告）。升级的实质不是加检查项，而是**接受"语义判断进入 lint"**——因此必须引入中间档：判断给 AI、裁决给人、执行给流程。

**拆分升级**（"流程化"的两半成本不对称，分开决策）：

| 组成 | 成本 | 决策 |
|------|------|------|
| 触发自动化：Ingest 阶段 D 后自动跑机械 lint | 零 LLM token（检查项全机械，grep / 版本比对 / backlinks） | **即刻采纳**（操作规程待同步） |
| 三档权限 + 语义检查项（矛盾 / 缺失 / 空白） | 每次 lint 一次 LLM 全库阅读 + 用户裁决交互 + AI 分档错误风险（分错档比不查更危险） | **等触发信号** |

**可观测的升级触发指标**（替代模糊的"高发"，满足其一即启动升级评估）：

| 信号 | 含义 |
|------|------|
| 月度人工发现 ≥2 次跨页矛盾，且 Disputed 流程处置吃力 | 语义矛盾成为真实负担 |
| 漂移复核频繁，且集中于无版本号文档 | 机械检测覆盖出现空洞 |
| 页面 >30 且查询中频繁遇到"该有页面的概念不存在" | 缺失 / 空白真实出现 |

**升级执行步骤**：

1. **先有数据**：依据 log 的 `## lint` 小节积累的检查记录（问题类型分布）挑选要引入的语义检查项——完整版六项（矛盾 / 过时 / 孤立 / 缺失 / 引用 / 空白）不必全抄，只抄数据证明高发的
2. **加中间档**：权限表从两档扩为三档；"需用户确认"档只收纳**改动知识内容**的处置（标记矛盾 / 过时、删孤儿页、新建对比 / 综述页），机械修复仍留在自动档
3. **分档判据成文**：每条检查项显式标注归属档位——防止 AI 分档漂移（这是三档方案最大的执行风险）
4. **分层调度**：沿用"Ingest 后自动轻量 lint"跑机械项；语义检查作为重档只在周期 lint（如月度）或用户主动触发时执行
5. **回滚条件**：若用户确认档的建议多数被否决（误报 / 分档错误率高），退回机械两档——升级本身也受 P1 约束

## 9. 增量更新与冲突治理（wiki 与代码同仓、多人协作）

> 本章为设计决策记录。操作规程（`skills/llm-wiki-lite.md`）与项目治理**暂未同步**本章内容，待治理实际启动时再落地（P1）。

### 9.1 前提与总纲

**前提**：长并发窗口是常态——短事务纪律（先 pull 再写、写完立即 push）在团队实践中不可依赖。因此设计目标不是"避免并发"，而是：**并发必然发生时，冲突要么被 git 自动合并，要么可机械秒解**。这是 P2 的又一次应用：短事务是嘱咐，结构是机制。

三个热点的处置：

| 热点 | 解法 | 出路类别 |
|------|------|---------|
| index.md | 本地缓存不提交 | **消灭状态** |
| log.md | 按来源分小节 + 全保留兜底 | **错开写入 + 冲突无害化** |
| 页面 | 一页一物文件级隔离（要素 1 已有）+ 语义合并兜底 | **错开写入** |

共享可变状态的四个出路：消灭状态、错开写入、冲突无害化、串行化（团队无全局锁，不可行）。每个热点按其语义选择——纯投影允许消灭，append-only 允许全保留。

### 9.2 index：从共享状态到本地缓存（投影消灭）

**数据 vs 投影的判据**：删除后能否零信息丢失地再生。index 的每一列都有再生来源（链接←文件名枚举、摘要←固定小节首句、版本←frontmatter），故为投影；log 的 append-only 历史含独有信息，故为数据。

| | log.md | index.md |
|---|--------|----------|
| 本质 | 数据 | 投影 |
| 处理 | 必须提交（团队共享的审计资产） | 不提交（gitignore / svn:ignore，本地缓存） |
| 冲突 | 全保留 | 不存在（永不进合并） |

**本地缓存规则**：

- 不提交 → 头号冲突热点消失，且不再需要投影合并纪律
- 本地**确定性重建**（枚举 → 提取固定小节首句 → 生成），触发时机：每次会话开始 / pull 之后；自检：枚举清单与 index 行不一致即重建
- **陈旧的 index 比没有更危险**（确定性入口给出错误答案 → 重复建页），故必须机械重建而非随手维护
- 重建成立的前提是投影纪律：摘要来源固定（con 页取 `## 定义` 首句、src 页取 `## 摘要` 首句），index 不携带独有信息
- 规模阶梯：<15 页无需 index（要素 1 使文件名即检索索引）；文件名扫描不足或出现人类导航需求时启用
- 新克隆冷启动：一次重建（分钟级、确定性）

**代价**：GitLab 网页浏览者看不到导航页（团队人均进 vault，可接受；将来若需要，另建手写导航页，属另一产物，不与本投影混同）。

**备选方案否决**：① index 分片多文件——仍是共享状态，冲突只是推迟；② 去掉 index 全靠搜索——违反要素 2；③ 提交 + 冲突时重建——可行但劣于不提交，多出一套投影纪律与合并流程。

### 9.3 log：结构错开 + 全保留兜底

**git 机制事实**：两人基于同一 base 各自在文件尾部追加不同内容 = 同一锚点的不同插入，3-way merge 必然冲突，GitLab 无法自动合并（xdiff 对同位置不同插入无裁决规则；SVN 下重叠修改更无自动合并）。

**结构错开**（利用"并发的两人几乎总在 ingest 不同来源"这一事实）：log 按来源分小节、小节按来源名排序插入（不加文件尾）、条目插入所属小节：

```markdown
## src-SkillBus架构设计文档
- [2026-08-21] ingest | con-能力契约 · Update · Cascade: con-能力执行与路由

## src-需求详情文档
- [2026-08-21] ingest | con-需求解析 · New
```

不同来源的并发写入落在文件不同区域 → git 行级合并自动通过。残余冲突面：并发 ingest 同一来源（来源有归属，几乎不发生）；并发 lint（末尾全局小节，全保留解决）。

**兜底规则**：log 冲突 = 两边条目全保留、按时间戳排序——append-only 的语义无损福利，确定性规则可交 AI 机械执行。

**升级路径**（P1）：分小节后仍频繁冲突 → log 目录化（一次 ingest 一个事件文件 `log/日期-来源.md`，不共享文件即零冲突，`grep -r` 台账照用）。

### 9.4 增量更新（四阶段，镜像 SkillBus 流水线架构）

SkillBus 的"确定性外壳包裹 LLM"（prescreen 零 LLM + LLM 只出语义）同样适用于 wiki 增量更新。地基：**变更检测靠 version 锚点（扩展 2），影响面靠 backlinks（扩展 6）**。

| 阶段 | 动作 | LLM / Token |
|------|------|------------|
| A 变更检测 | 版本漂移检测的输出即待处理清单；兜底 `git diff --name-only` 对照上次 ingest 点 | 零 LLM（纯命令 / grep） |
| B 影响面分析 | 读 **diff 不读全文**；`get_backlinks([[src-xxx]])` 取受影响页面；Triage 在此声明 disposition | 低（O(变更) 而非 O(文档)） |
| C 增量编译 | 输入 = diff + 受影响页；**输出 = 最小补丁，不整页重写**；locate-before-write 只核对 diff 引入的新字面量 | 集中投入处 |
| D 确定性收尾 | version/date 刷新、index 重建、log 分小节追加 | 零 LLM |

Token 经济学：读源从整篇降到 diff；定位页面从全库搜索降到一次反链调用；写页面从整页重写降到最小补丁；lint 只跑漂移报警的页面。输出最小补丁同时避免"整页重写顺手润色无关段落"造成的语义漂移。

### 9.5 冲突解决规则表

| 冲突文件 | 解决规则 | 执行者 |
|---------|---------|--------|
| index.md | 不存在冲突（本地缓存） | — |
| log.md | 两边条目全保留，按时间戳排序 | AI 可机械执行 |
| 页面内容 | 语义合并（LLM 重新 compile 或人工） | 需判断，人/AI 协作 |

### 9.6 日志增长量化

重度使用（karpathy 生产强度，周 87 条）≈ 年 4500 条 ≈ 1 MB；一般团队 ≈ 年数百 KB。增长不构成问题——log 的消费方式（追加 / 尾部 / grep）从不依赖全文读取；唯一真实风险是某次会话把整个 log 读入上下文，以 §4.5 访问纪律防范（防访问方式，不防长度）。分卷 `log-YYYY.md` 为升级路径项。

## 10. 知识库质量度量维度

> 设计动机：知识库的"质量"不能只由 wiki 自身属性定义——结构再工整、保真再完美，若用户真实查询时频繁查不到、被迫回源、绕很多弯，体验就是差。业界（Doctor 诊断层、obsidian-wiki-health）普遍卡在"供给侧结构健康"，与查询体验松绑定甚至割裂。本章把度量分为两层，并明确需求侧度量来自真实查询动作的执行结果，天然不割裂。

### 10.1 两层定位

| 层 | 数据来源 | 回答的问题 | 性质 |
|----|---------|-----------|------|
| **供给侧** | 直接读 wiki 文件本身 | wiki 写得好不好（规整/忠实/覆盖） | 门槛指标：不过关必差 |
| **需求侧** | 记录真实查询动作（工具调用流） | 用户查得顺不顺 | 体验指标：直接绑查询结果 |

**关键边界（呼应 §7 负面清单）**：本度量**不产出"置信度/质量分数"这类无校准依据的假精度**。供给侧重机械事实核查（保真/断链/覆盖，可脚本判定），需求侧重行为统计聚合（回源率/失败率，来自真实调用流），两者均非主观打分。综合分仅作可选内部参考，不作为对外质量断言。

### 10.2 供给侧维度（基础健康，必要但不等于质量）

全部可机械核查，零 LLM，复用 `wiki_check.py` 与 obsidian-mcp-pro。

| 维度 | 看什么 | 实现要点 | 现有落点 |
|------|--------|---------|---------|
| **结构完整性** | 入口（index/log）在否、双链断否、孤儿页否、坐标齐否 | 文件存在性 + `find_broken_links`/`find_orphans`/`get_outlinks` + frontmatter 解析 | wiki_check 证据扫描 |
| **保真度** | 字面量是否忠于源、版本是否漂移、Status 块是否合规 | 字面量提取→源文档逐字核对；version 锚点比对；Status 块三要素正则 | wiki_check Fidelity/Drift |
| **静态覆盖度** | 源文档章节/术语有多少被 wiki 吸收 | 取 `raw` 源文档章节树（标题解析），与"吸收文本"（src 页正文 ∪ 所有 `[[src-xxx]]` 指向它的页面正文）做子串命中比对 | `wiki_coverage.py`（零 LLM，冷启动代理） |

**度量输出**：`断链数`、`孤儿数`、`坐标完整率`、`literals/suspects/drift/evidence_errors`、`coverage_avg`。
**诚实边界**：静态覆盖度是"我以为你粗"，不等于用户真觉得粗——仅作冷启动兜底与结构性缺口发现，不单独当作质量。

### 10.3 需求侧维度（真实查询效果，核心增量）

**前提**：需求侧一切建立在"采集真实查询行为"之上——即每次查询 Agent 通过 obsidian-mcp-pro 实际走了哪些工具调用（读哪个 wiki 页、回哪个源、搜了什么词、有没有报错）。采集应零 LLM、从工具调用层取得，不靠模型自报。

| 维度 | 看什么 | 怎么算 | 为什么有意义 |
|------|--------|--------|------------|
| **4 回源依赖度** | 每次查询需回 `docs/` 原文的比例 | 单次查询回源次数 / (回源+wiki消费)；全局同理 | 回源多=wiki 表达层不够用（用户用脚投票的粗） |
| **5 失败/受阻率** | 工具调用返回错误的频率 | `Note/Section not found`、搜索空结果计为失败；按路径前缀聚合 | 暴露导航缺陷与召回失败（RAGAS 上下文召回的零成本代理） |
| **6 检索命中率** | 用户搜的词 wiki 能否接住 | 搜索返回空=未命中；未命中 query 聚类=待建主题候选 | 覆盖度看不到"用户实际关心什么" |
| **7 路径长度/跳数** | 为答一问跨几页、回源几次 | 单次查询调用链长度；按入口/枢纽/来源/原文分层漏斗 | 跳数高=知识碎片化、组织差 |
| **8 refine 触发率** | 查询后用户是否频繁要求补全 | "查询→紧邻 refine"相邻动作对占比；按被 refine 源文档聚合 | "这里太粗"最直接的用户标签 |

**维度 4 增强——关联回源（用 raw 坐标去歧义，零 LLM）**：
若一次查询中**先读 `wiki/sources/src-X.md`、后读其 `raw` 坐标 `docs/X.md`** → 高置信"wiki 不够用"信号；若未读任何 wiki 页直接读 `docs/X.md` → 用户主动要原文（低置信，不计入缺口）。判定纯靠 frontmatter `raw` + 调用时序。

**维度 7 展开——路径长度的两层算法**：
- **调用链总长**：一次查询的工具调用总数，全局取平均。
- **导航漏斗**（更具诊断价值）：按 `get_note` 的 path 前缀分层——`wiki/index.md`=入口、`wiki/concepts|syntheses`=枢纽、`wiki/sources`=来源、`docs/**`=原文；看各层转化率，定位"多出来的跳"卡在哪层（如大量查询从枢纽直落原文=con 页没起摘要作用）。
- 与维度 4 区别：维度 4 看"回源占比"（内容够不够细），维度 7 看"总跳数"（组织好不好聚）；内容全但散得绕，两者互补。
- 误区：跳数非越低越好（跨多源对比本就多跳）；看分布、盯异常高跳+伴随失败/回源的高跳。

### 10.4 查询归并判定（需求侧的前置子维度）

需求侧所有维度都依赖"把一串工具调用归并成一次查询"。归并不准，后续指标精度下降——但指标是统计性的，方向不崩（不同于事实类指标非黑即白）。

**分层判定（不必全程烧 LLM）**：

| 层 | 方法 | 是否 LLM | 说明 |
|----|------|---------|------|
| 1 动作分类 | 按工具名切分 query/ingest/lint 边界 | 零 | `search_*`/`get_*` 为查询类；ingest/lint 调用直接切断 |
| 1 用户消息锚定 | 以用户每条提问为查询单元起点 | 零 | 最可靠边界：用户消息节奏即天然查询分界 |
| 2 时间间隙 | 同消息内相邻调用间隔>阈值(如5~10min)再切 | 零 | 启发式，防长思考被误并 |
| 2 路径连贯性 | 路径突跳到无关主题疑似新目标 | 零 | 启发式辅助 |
| 3 语义判定 | 对仍模糊的边界，用用户原话+调用列表做一次判定 | 极少 | 仅兜底，上下文极短 |

**判定不准的后果可控**：回源率/跳数仅是分母微扰、趋势仍在；refine 触发以"用户消息→refine 相邻"判定几乎不依赖归并。

### 10.5 从指标到行动：按源文档聚合

需求侧八维度单独看是噪音，**真正有价值的是按 `raw` 坐标聚合到每个源文档**：

```
每个源文档 doc-X：
  关联回源次数（维度4增强）
  失败次数（维度5）
  被 refine 次数（维度8）
  其章节被搜空次数（维度6）
        ↓ 汇总
  doc-X 的"表达层充分度不足分"
        ↓ 降序
  refine 优先级清单
```

这即把需求侧信号从"一次查询的噪音"变成**可排序、可优先处理的行动队列**——质量度量真正驱动动作。

### 10.6 闭环验证：refine 前后对比

最有价值的一步——**refine 某文档前记录其回源率/失败率基线，refine 后观察是否下降**：下降=改善有效，不降=可能组织方式错了而非内容少。使质量度量不止"发现问题"，还"验证修复"，形成闭环。

### 10.7 诚实边界

| 边界 | 说明 |
|------|------|
| 冷启动空洞 | 刚建库无查询，需求侧全空；此时仅靠供给侧覆盖度兜底，等查询积累再切行为指标 |
| 采集覆盖率 | 仅记录走 obsidian-mcp-pro 的调用；用户在 Obsidian UI/其他工具查记录不到，须标注范围 |
| 供给侧非体验 | 供给三维是门槛不是质量，不过关必差但过关不代表体验好 |

#### §10.8 实施方案（采集↔聚合两端分工与落点）
§10.3 的前提"在工具调用层、零 LLM 采集真实查询行为"，由**两端各司其职**落地：obsidian-mcp-pro 只发射原始事件（不懂 wiki 结构），llm-wiki-lite 只做聚合（不懂 obsidian 协议）。两端靠一个稳定的事件 Schema 解耦，且**度量不自动写库、不产出质量分数**（§10.7 诚实边界）。

**1. 采集端：obsidian-mcp-pro（发射，不聚合）**

- 落点：`src/lib/monitor.ts`（遥测发射器）+ `src/lib/tool-seam.ts` 的 `defineTool`（唯一 hook 点，全 41 工具经此注册，一处改动即覆盖全部）。
- 开关：`OBSIDIAN_TELEMETRY` 环境变量，默认不设置即零开销关闭；取值：
  - 未设置/空 → 不发射（no-op）
  - `"stderr-json"` → 每调用一行 JSON 写到 stderr
  - 任意文件路径 → 追加写入该文件（一行一事件）
- 事件 Schema（`CallEvent`，每次调用发射一条，纯原始字段、不含 wiki 知识）：
  ```jsonc
  {
    "ts": "ISO-8601",            // 调用返回/抛错时刻
    "tool": "get_note",          // 工具名（seam 注册名）
    "vault": "/abs/vault/root",  // 多 vault 解析后的生效根
    "path": "wiki/sources/...",  // 触碰的 vault 相对路径（可选）
    "query": "...",              // search_* 的检索串（可选）
    "isError": false,            // handler 出错或抛异常
    "contentItems": 1,           // MCP 结果 content 块数
    "primaryTextBytes": 100,     // 首文本块字节数（结果体量代理）
    "durationMs": 5              // handler 耗时
  }
  ```
- hook 实现：在 `defineTool` 的 `cb` 里，成功路径（`handler` 返回后）与失败路径（`catch` 内）各发射一次 `recordCall(...)`。字段提取抽成两个纯函数，只读取白名单键，避免把笔记正文/附件塞进遥测流：
  - `extractTelemetryArgs(args)`：仅取 `path` / `query` / `folder` 等少量键；
  - `resultMetrics(result)`：从 MCP `ToolResult` 算 `contentItems` 与 `primaryTextBytes`。
- 设计约束：发射层**不做**路径分类、不做查询归并、不计算任何 §10.3 指标——保持通用 Obsidian 服务器本质，wiki 结构知识不泄漏进 mcp。
- 测试：`src/__tests__/tool-seam.test.ts` 通过 `setTelemetrySink` 注入内存 sink，断言发射发生在成功与抛错两条路径、以及 `extractTelemetryArgs`/`resultMetrics` 的字段捕获。

**2. 聚合端：llm-wiki-lite（聚合，零 LLM）**

- 落点：`scripts/wiki_metrics.py`（确定性脚本，Python 3.8+ 标准库，无第三方依赖）。复用 `wiki_check.py` 的 `parse_frontmatter`/`raw_values` 解析 `raw` 坐标。
- 数据流：`§10.4 查询归并 → §10.3 维度4-8 → §10.5 按源聚合 → §10.6 闭环对比`。
- §10.4 查询归并（三层零 LLM 启发式）：① 动作分类（非查询工具如 ingest/lint/refine 切断查询）；② 时间间隙（相邻调用 > `gap_seconds` 默认 600s 切断）；③ 路径连贯性（间隙过半且顶层目录跳变切断）。多 vault 场景下过滤发生在归并**之前**，按 `event.vault` 严格隔离，杜绝跨库归并污染。
- 维度计算（`compute_dimensions`）：
  - **[4] 回源依赖度** = 原始文档读取数 / (原始文档读取 + wiki 页消费数)；增强项"关联回源信号"用 `raw` 坐标高置信判定（查询内先读 `wiki/sources/src-X` 再读其声明的 `docs/...`）；另计"直接回源低置信"分支（未读任何 wiki 页直接读 docs，不计入缺口）。
  - **[5] 失败/受阻率** = `isError` 调用数 / 调用总数，并额外按 path 前缀分布（`docs=1` 等）暴露哪层导航缺陷。
  - **[6] 检索命中率** = 1 − 搜索未命中数 / 搜索调用数；未命中用"单块短回文"代理（`primaryTextBytes < --miss-bytes`，默认 80），并将未命中 query 聚成"待建主题候选"。
  - **§10.5 知识缺口（gap-to-action，零 LLM）**：对每个未命中 query，归一化后与 vault 全部 wiki 页正文+标题做子串比对分类——命中现有页 → `STALE_SEARCH`（知识在但检索词没接住，改进索引/双链/别名，非录入）；全库无 → `MISSING`（真没录，按频次降序列为"待录入主题候选"）。报告新增 `=== Knowledge gaps (actionable, §10.5) ===` 块，直接告诉 AI「该录什么 / 该补什么索引」，把行为噪音转成可执行动作。
  - **[7] 路径长度/跳数** = 单查询调用链总长均值 + 导航漏斗（entry/hub/source/raw 分层计数）。
  - **[8] refine 触发率** = "查询动作 → 紧邻 refine 动作"相邻动作对占比；按被 refine 的源文档聚合并入 §10.5。
- §10.5 按源聚合（`aggregate_by_source`）：用 `raw` frontmatter 坐标把信号滚到每个 `docs/X.md`，算"表达层不充分度"=`关联回源×3 + 失败×2 + 搜索空×2 + 已refine×1`，降序输出 refine 优先级队列。
- §10.6 闭环对比：`--baseline <file> --report compare` 对比 refine 前后回源率/失败率/命中率/跳数；回源率或失败率下降即判定 refine 有效。
- 诚实边界（§10.7）：报告尾部固定声明仅记录 mcp 调用、检索未命中为代理近似、不给质量分数。
- 测试：`scripts/test_wiki_metrics.py`（纯 `unittest`，`python -m unittest test_wiki_metrics.py`）用 `tempfile` 造真实 vault + 合成事件，断言各维度数值与 BOM/空行解析鲁棒性。

**3. 两端契约（Schema 即接口）**

| 字段 | 类型 | 来源（mcp） | 消费（llm-wiki-lite） |
|---|---|---|---|
| `ts` | string | `new Date().toISOString()` | §10.4 时间间隙 |
| `tool` | string | `spec.name` | 动作分类（query/search/refine 正则） |
| `vault` | string | 多 vault 解析结果 | 多 vault 隔离过滤 |
| `path` | string? | `extractTelemetryArgs` 白名单 | §10.5/§10.7 路径分类与聚合 |
| `query` | string? | search_* 入参 | §10.6 未命中聚类 |
| `isError` | bool | handler 抛错/返回错 | §10.3 维度5 |
| `contentItems`/`primaryTextBytes` | int | `resultMetrics` | §10.3 维度6 代理 |
| `durationMs` | int | `Date.now()-started` | 可选诊断 |

契约稳定性要求：mcp 端新增字段须向后兼容；llm-wiki-lite 端对缺失字段取默认值（如 `path`/`query` 缺失不报错）。
